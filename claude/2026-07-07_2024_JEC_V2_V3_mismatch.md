# 2026-07-07 작업 정리: 2024 era Jet Energy Correction `map::at` 크래시 수정

## 증상

`SKNano.py -a DY -i TTLL_powheg -e 2024 ...`로 제출한 job (job_1.cc/job_2.cc)이 첫 이벤트의 Jet
처리 단계(`Jet_area` 브랜치 활성화 직후)에서 아래 에러로 죽음. HNWR뿐 아니라 DY 등 다른 analyzer에서도
동일하게 재현됨 (analyzer 코드 문제가 아님을 시사).

```
terminate called after throwing an instance of 'std::out_of_range'
  what():  map::at
```

## 원인

`AnalyzerTools/src/MyCorrection.cc`의 `MyCorrection` 생성자(era="2024" 설정 부분, 구 라인
124~136)에 2024 JEC(Jet Energy Correction) 태그가 `"Summer24Prompt24_V2_..."`로 하드코딩되어
있었는데, 실제 `CMS_corrections/JME/Run3-24CDEReprocessingFGHIPrompt-Summer24-NanoAODv15/latest/jet_jerc.json.gz`
파일 안에는 `V2` 태그가 없고 **`V3`** 태그만 존재함 (`zcat`으로 압축 풀어서 correction 이름 목록을 직접
확인). JME POG쪽에서 correction 파일을 V2→V3로 업데이트했는데 코드의 하드코딩 문자열이 따라가지 못한
것 (제가 이전에 수정한 Muon/FatJet 코드와는 무관).

`MyCorrection::GetJESSF()` (`MyCorrection.cc` 약 1467번째 줄)에서

```cpp
string cset_string = JME_JES_GT.at(GetEra().Data());   // "..._V2_..." (존재하지 않는 태그)
cset = cset_jerc->compound().at(cset_string);           // 파일에 없는 키 조회 → std::out_of_range
```

이 예외를 던짐.

같은 이유로 `JME_JER_GT["2024"]`도 `"Summer23BPixPrompt23_RunD_JRV1_MC_######_AK4PFPuppi"`로
되어 있었는데, 실제 파일 키는 `"Summer24Prompt24_JRV1_MC_PtResolution_AK4PFPuppi"` 등이라 마찬가지로
불일치. JES를 고쳐도 JER 계산(smearing) 단계에서 같은 종류의 크래시가 이어졌을 것.

## 수정

`AnalyzerTools/src/MyCorrection.cc`의 2024 era 태그 설정 블록을 실제 파일 내용에 맞게 수정:

```cpp
if (!IsData) {
  JME_JER_GT["2024"] = "Summer24Prompt24_JRV1_MC_######_AK4PFPuppi";
  JME_JES_GT["2024"] = "Summer24Prompt24_V3_MC_######_AK4PFPuppi";
} else {
  // JER not used for data
  JME_JES_GT["2024"] = "Summer24Prompt24_V3_DATA_######_AK4PFPuppi";
}
```

(DATA용 JER GT는 원래도 안 쓰이므로 그대로 비워둠.)

## 확인 방법

- `zcat CMS_corrections/JME/.../latest/jet_jerc.json.gz`를 파싱해서 `"name"` 필드들을 모아
  `2024`/`Summer24` 포함 항목만 추려서 실제 태그 이름을 확인함 → `V3`, `Summer24Prompt24_JRV1_...`만 존재.
- 빌드/재실행은 사용자가 직접 확인.
